# Fox：Markdown AI 伴读工具项目规划书

**版本：** V1.0  
**阶段：** MVP 规划  
**产品名称：** Fox（暂定，正式发布前完成名称与商标检索）  
**产品定位：** 支持自定义 AI 服务的 Markdown 阅读与问答桌面工具

---

## 一、项目概述

### 1.1 项目背景

在阅读技术文档、学习笔记或项目说明时，用户经常需要借助 AI 理解其中的概念和段落。常见操作是将文字复制到聊天工具，再切回文档继续阅读，过程会打断思路，后续追问也容易丢失上下文。

Fox 参考 Zed 的分栏交互方式：

- **右侧阅读 Markdown 文档。**
- **左侧围绕文档与 AI 对话。**
- **选中文字后直接解释或补充问题。**

第一阶段不建设完整编辑器或知识库，而是聚焦一个清晰的使用场景：

> 读到不懂的地方，选中它，即可获得有上下文的解释，同时保持阅读位置不变。

### 1.2 产品目标

1. 降低阅读时向 AI 提问的操作成本。
2. 让用户清楚知道 AI 使用了哪些文档内容。
3. 支持用户配置自己的 AI 服务和密钥。
4. 以安静、友好的狐狸形象建立产品识别度。
5. 以小而完整的 MVP 验证持续使用价值。

### 1.3 目标用户

| 用户类型 | 主要需求 |
|---|---|
| 开发者 | 理解 README、技术文档、设计方案及代码片段 |
| 学生与学习者 | 阅读 Markdown 学习材料、解释概念、梳理论证 |
| 知识工作者 | 阅读笔记与研究资料，快速总结和追问 |
| 已有 AI API 的用户 | 使用自有服务，控制模型选择与使用成本 |

## 二、产品定位与范围

### 2.1 核心价值

**Fox，陪你读懂每一段。**

与普通聊天工具相比，Fox 的重点不是增加更多聊天功能，而是将阅读、选区引用、上下文管理和追问整合在同一界面。

### 2.2 MVP 范围

| 模块 | 第一版支持 |
|---|---|
| 文档格式 | 本地 Markdown 文件 |
| 阅读方式 | 只读预览，不修改原文件 |
| 界面布局 | 左侧 AI 对话，右侧文档阅读 |
| AI 接入 | 自定义 Base URL、API Key、模型名称 |
| 接口协议 | OpenAI-compatible Chat Completions |
| 提问方式 | 解释选区、引用选区提问、围绕当前文档提问 |
| 对话能力 | 连续追问、流式输出、停止、复制、失败重试 |
| 数据保存 | 本地保存配置、会话、引用快照、阅读位置 |
| 品牌形象 | Fox 静态 Logo、基础耳朵与尾巴交互 |

### 2.3 暂不支持

- PDF、Word 等其他文档格式。
- Markdown 编辑、AI 自动改写原文件。
- 多文档联合问答、向量数据库和知识库。
- 联网搜索、插件和工具调用。
- 语音输入、语音播放。
- 账户系统、云同步和团队协作。
- 任意厂商原生接口的自动兼容。

**边界说明：** 自定义 Base URL 不代表支持所有 AI 接口。第一版只保证已验证的 OpenAI-compatible 协议范围，其他协议通过后续适配器扩展。

## 三、核心用户流程

### 3.1 首次使用

```text
启动应用
   ↓
配置 AI 服务
Base URL / API Key / 模型名称
   ↓
发送测试请求
   ↓
打开或拖入 Markdown 文件
   ↓
阅读文档
   ↓
选中文字 → 解释 / 加入提问
   ↓
确认发送范围，提交问题
   ↓
查看 AI 回答并继续追问
```

允许用户先打开文档阅读，在首次提问时再配置 AI。

### 3.2 典型使用场景

**场景 A：解释段落**

用户选中一段文字，点击“解释”，Fox 在左侧展示引用并流式回答，右侧保持原阅读位置。

**场景 B：带着问题阅读**

用户选中文档中的方案描述，点击“加入提问”，输入：

> 这个方案和上一节的方法有什么区别？

**场景 C：理解全文**

用户不选择文本，直接输入：

> 总结这篇文档的核心观点，并说明需要提前了解哪些概念。

文档超过上下文预算时，应用提示调整范围，不静默截断后声称已理解全文。

## 四、功能需求

### 4.1 双栏工作区

默认左侧为 AI 面板，右侧为 Markdown 阅读区，支持拖动分隔线调整宽度。

```text
┌─────────────────────────┬──────────────────────────────────┐
│ Fox · 随时可以提问      │ README.md              打开文件  │
│ 当前模型 / 文档位置     │                                  │
├─────────────────────────┤ # 项目说明                       │
│ 引用卡片                │                                  │
│ “选中的文档内容……”      │ Markdown 阅读内容                │
│                         │                                  │
│ 用户的问题              │ 选中文字：                       │
│ AI 的解释               │ [解释] [加入提问]                │
│                         │                                  │
├─────────────────────────┤                                  │
│ 上下文范围 / 发送预览   │                                  │
│ 输入问题……  发送/停止   │                                  │
└─────────────────────────┴──────────────────────────────────┘
```

交互要求：

- 提问和接收回答时不改变右侧阅读位置。
- 用户向上翻阅聊天记录时，不强制滚动到底部。
- 引用内容显示为独立卡片，支持移除。
- 当前文件、模型、生成状态清晰可见。
- 点击狐狸形象统一聚焦提问输入框，不随状态改变操作含义。

### 4.2 Markdown 阅读

支持：

- 打开和拖入 `.md`、`.markdown` 文件。
- 标题、列表、引用、链接、表格、任务列表。
- 代码块和语法高亮。
- 文本选择与复制。
- 当前文档目录内的相对路径图片。
- 阅读位置恢复。

安全约束：

- 不执行 Markdown 中的脚本，原始 HTML 默认禁用。
- 本地图片访问限制在授权文档目录内，校验路径越界。
- 远程图片默认不加载，用户确认后再请求。
- 外部链接经安全协议检查后由系统浏览器打开。

公式、Mermaid、文档目录与全文搜索放入后续版本。

### 4.3 自定义 AI 服务

配置字段：

| 字段 | 说明 |
|---|---|
| 配置名称 | 区分不同服务 |
| Base URL | 例如 `https://example.com/v1` |
| API Key | 云端服务通常需要，本地服务允许为空 |
| 模型名称 | 手动填写服务提供的模型 ID |
| 上下文预算 | 高级配置，限制发送规模 |

第一版支持保存多套配置，每次请求使用一套。

接口行为：

- 基于 Base URL 拼接 `/chat/completions`，不重复添加 `/v1`。
- 使用 Bearer API Key 鉴权。
- 支持流式响应、请求取消、超时和异常提示。
- 不依赖 `/models` 接口，模型名称可手动填写。
- 远程服务要求 HTTPS；本机服务允许 HTTP。

“测试连接”发送短消息验证接口、鉴权和模型可用性，并提示可能产生少量费用。

### 4.4 AI 对话

提供三种入口：

1. **解释选区：** 使用预设解释指令直接发起请求。
2. **加入提问：** 添加选区引用，由用户补充问题。
3. **直接提问：** 围绕当前文档问答。

基础能力：

- 流式显示回答。
- 停止生成。
- 复制回答。
- 失败后手动重试。
- 新建会话。
- 同一会话内连续追问。

请求失败时区分鉴权错误、模型不存在、限流、接口不兼容和网络异常。避免无限自动重试导致重复计费。

### 4.5 上下文管理

#### 模式 A：选区上下文

默认包含：

- 当前问题。
- 选中的原文。
- 所属标题与邻近段落。
- 预算内的最近对话。

开发时保留 Markdown 源文本与渲染节点的位置映射，便于准确提取选区所在段落。

#### 模式 B：当前文档

- 预算内发送全文。
- 超出预算时，提示用户选择局部内容或明确接受部分范围。
- 始终说明实际发送范围，不将部分文档描述为完整阅读。

#### 通用规则

- 优先保留当前问题和选中原文。
- 预留回答所需空间。
- 按预算裁剪历史对话，并标记历史范围变化。
- 提供“本次发送内容”预览。
- 未知模型使用保守 token 估算，不声称精确计算。
- 文档作为待分析资料处理，其中的指令不得覆盖应用规则。

第一版不建设 RAG；上下文清晰可控优先于自动检索能力。

### 4.6 本地记录

本地保存：

- 服务配置及密钥引用。
- 文档路径、标识、内容哈希和阅读位置。
- 会话与消息。
- 提问引用快照和发送范围元数据。

默认不将文档全文额外复制进数据库，也不保存完整请求载荷；但引用快照、提问和回答仍可能包含敏感信息。

文件内容变化时，提示历史回答可能基于旧版本。删除会话时同步删除其消息与引用快照。

## 五、品牌视觉与 Fox 交互

### 5.1 形象方向

以目前确认的精修狐狸图片作为**基础造型参考**：

- 温暖橙色主体。
- 奶油色面部、胸前及尾尖。
- 深炭灰五官和局部色块。
- 画面左侧的大尾巴。
- 双耳竖起，表情安静友好。
- 坐姿紧凑，适合桌面应用与伴读助手。

当前图片尚不是可直接用于动画的分层资产，需要矢量重绘。

### 5.2 正式素材整理

保留现有造型，不继续大幅重设计，重点完成：

1. 清理眼睛附近的小突起与多余节点。
2. 将轻微渐变整理为统一纯色。
3. 检查奶油色尾尖在浅色背景上的对比度。
4. 简化小尺寸下容易粘连的脚部、耳缘与胸前细节。
5. 制作深浅背景适配版本。
6. 补齐动画部件的遮挡区域。

建议交付：

| 文件 | 用途 |
|---|---|
| `fox-master.svg` | 完整角色主视觉 |
| `fox-animated.svg` | 耳朵、尾巴、头部、身体分组的动画素材 |
| `fox-small.svg` | 小尺寸简化标记 |
| `fox.png` | 透明背景展示素材 |
| 平台图标资源 | 按目标操作系统规范导出 |

AI 生成的“矢量风格图片”不等同于真正的 SVG，需人工或设计工具重绘检查。

### 5.3 尾巴：辅助表达阅读位置

设计原则：

> 用姿态表达文档位置，用短暂摆动反馈阅读动作，不持续打扰用户。

| 状态 | 表现 |
|---|---|
| 文档开头 | 尾巴自然收拢 |
| 阅读向后推进 | 尾巴逐步舒展、轻微抬起 |
| 滚动停止 | 轻摆一次后静止 |
| 到达文末 | 尾尖轻动一次 |

约束：

- 根据滚动位置估算，不代表用户真正读懂或读完。
- 快速滚动不重复触发动画。
- 不足一屏的文档保持默认姿态。
- 悬停或键盘聚焦时可显示“文档位置 65%”。
- 动画只做小角度变化，避免尾巴遮挡其他界面。

### 5.4 耳朵：辅助表达 AI 状态

| 状态 | 视觉表现 | 文字反馈 |
|---|---|---|
| 未配置服务 | 自然放松 | 配置 AI 服务 |
| 准备就绪 | 双耳竖起 | 随时可以提问 |
| 等待响应 | 轻动一次 | 正在等待回答 |
| 正在生成 | 保持专注 | 正在回答… |
| 请求失败 | 略微放低 | 请求失败，点击重试 |

第一版可复用少量姿态，不必为每个状态制作独立动画。

“倾听”只是角色隐喻。没有语音功能时，不使用麦克风或“正在录音”等误导性表达。

### 5.5 动效与无障碍

- 全局只保留一个主要动态狐狸，不在每条消息旁播放动画。
- 动画不承载唯一状态信息，始终配合文字或图标。
- 提供“减少动画”设置，并跟随系统偏好。
- 减少动画模式下保留静态形象和文字状态。
- 状态变化不强制移动键盘焦点。

## 六、技术方案

### 6.1 产品形态

建议采用**本地桌面应用**。

主要理由：

- 适合读取本地 Markdown。
- 可使用系统凭据库保护 API Key。
- 原生网络层不受浏览器 CORS 约束，但仍需处理证书、代理和网络错误。
- 不需要建设业务服务器或代转用户请求。

### 6.2 推荐技术栈

| 模块 | 技术建议 |
|---|---|
| 桌面框架 | Tauri 2 |
| 前端 | React + TypeScript |
| 样式 | Tailwind CSS |
| 状态管理 | Zustand |
| Markdown | react-markdown + remark-gfm |
| 代码高亮 | Shiki，按需加载 |
| 本地数据 | SQLite |
| 密钥 | 系统凭据库 |
| AI 请求 | Rust HTTP 客户端 + SSE 解析 |
| Fox 动画 | 分层 SVG + CSS transform |
| 测试 | 单元测试、接口模拟、打包应用验收 |

### 6.3 系统架构

```text
界面层
├── Markdown 阅读区
├── AI 对话区
├── 服务配置
└── Fox 状态与动画
        │
        ▼
本地应用层
├── 文档读取与权限控制
├── 上下文组装与预算管理
├── AI Provider 适配层
├── 流式响应与取消
├── SQLite 数据管理
└── 系统凭据库访问
        │
        ▼
用户指定的 AI 服务
```

首版仅实现 OpenAI-compatible 适配器，保留后续扩展其他协议的接口。

### 6.4 数据实体

| 实体 | 主要内容 |
|---|---|
| ProviderConfig | 名称、Base URL、模型、密钥引用、预算 |
| Document | 稳定 ID、路径、内容哈希、阅读位置 |
| Conversation | 所属文档、标题、创建时间 |
| Message | 角色、内容、生成状态、服务与模型快照 |
| ContextSnapshot | 选区原文、标题路径、发送范围 |

## 七、隐私与安全

### 7.1 数据处理原则

**本地存储，直连用户指定服务，不经过项目方服务器。**

不能宣传为“数据绝不离开设备”，因为提问会向指定服务发送文档上下文。

### 7.2 首版必须落实

1. API Key 不写入 localStorage、普通配置文件或日志。
2. 保存后的密钥不再回传界面展示，只显示配置状态。
3. 系统凭据库不可用时，允许仅在本次运行中使用，不静默降级为明文保存。
4. 首次向某个服务发送内容前，展示目标域名和数据发送说明。
5. 日志排除 Authorization 头、文档正文和完整请求载荷。
6. 默认无遥测上传。
7. 停止生成时取消本地请求，并说明不能保证服务端停止计算或计费。
8. Markdown 不具有执行代码、调用工具或任意读取文件的权限。
9. 本地会话数据库首版不默认承诺加密，需要明确告知用户。

## 八、开发计划

### 8.1 估算前提

建议按以下条件规划：

- 1 名熟悉 React 与桌面开发的全栈工程师。
- 兼职设计与测试支持。
- 首发一个操作系统。
- 不包含账户、云同步、多平台发布和自动更新。
- Fox 矢量素材制作可与开发并行。

预计 **5～6 周**。首次使用 Rust/Tauri、签名公证或设计素材返工可能增加周期。

### 8.2 阶段安排

| 阶段 | 时间 | 交付内容 |
|---|---|---|
| 需求与技术验证 | 第 1 周 | 界面原型、协议约定、流式请求及密钥存储验证 |
| 阅读基础能力 | 第 2 周 | 双栏布局、Markdown 渲染、选区引用、Fox 静态素材 |
| AI 问答闭环 | 第 3 周 | 服务配置、连接测试、流式回答、停止和重试 |
| 上下文与记录 | 第 4 周 | 发送预览、预算管理、本地会话、阅读位置恢复 |
| 动效与内测 | 第 5 周 | Fox 基础动画、异常处理、安全与性能测试 |
| 发布缓冲 | 第 6 周 | 反馈修复、安装包、帮助文档、发布准备 |

**第 3 周里程碑：**

> 打开文档 → 选中文字 → 提问 → 获得 AI 解释。

如果时间不足，优先保证阅读与问答闭环，Fox 动画可降级为静态状态切换。

## 九、验收标准

### 9.1 功能验收

- 常见 Markdown 内容正确显示。
- 自定义服务配置可保存、测试和切换。
- 至少验证两个独立实现的兼容服务。
- 若宣称支持本地服务，测试中必须包含一个本地实现。
- 选中文字后可直接解释或加入提问。
- 支持连续追问、流式输出、停止、复制和重试。
- 发送范围可查看，超预算不会静默处理。
- 重启后恢复会话与阅读位置。

### 9.2 稳定性与安全验收

- 无效密钥、无效模型、限流、断网均有明确反馈。
- 流式中断后保留已有内容并标记未完成。
- 不因切换文档将回答归入错误会话。
- API Key 不出现在明文配置、数据库字段或日志中。
- Markdown 脚本和本地路径越界访问被阻止。
- 在约定测试机上，约 1 MB 的常规 Markdown 目标为 2 秒内可阅读；大量图片及超大代码块单独测试。

### 9.3 视觉验收

- Fox 在深浅主题下轮廓清晰。
- 完整图标在 32、64、128 px 下检查可读性。
- 16–24 px 使用简化标记。
- 耳朵和尾巴动画无露底、断裂或明显抖动。
- 滚动过程中不会持续干扰阅读。
- 减少动画模式有效。

### 9.4 用户验证

邀请 5～10 名目标用户完成真实阅读任务，观察：

- 能否顺利配置自有 AI 服务。
- 是否理解发送了哪些内容。
- 选区提问是否比复制到聊天工具更方便。
- 回答后能否顺畅继续阅读。
- Fox 动效是帮助理解状态，还是造成干扰。
- 是否愿意在下一次阅读时继续使用。

默认通过访谈和自愿反馈收集结果，不依赖隐式遥测。

## 十、主要风险与应对

| 风险 | 应对方案 |
|---|---|
| 不同服务的兼容程度不一致 | 明确协议边界，维护已验证服务与已知限制 |
| 长文档超出模型预算 | 展示发送范围，提供局部提问，不声称全文理解 |
| AI 解释不准确 | 强调回答需核对原文，不承诺事实正确 |
| 文档包含提示词注入 | 将文档作为资料隔离处理，不提供工具执行权限 |
| Fox 动效影响专注 | 低频短动画、减少动画开关、静态降级 |
| 图片难以直接动画化 | 先做矢量重绘与遮挡区域补齐 |
| 名称或图形与已有品牌相似 | 正式商用前完成名称、图形和商标检索 |
| MVP 范围膨胀 | 将编辑器、知识库、多文档与云服务放在后续阶段 |

## 项目结论

Fox 第一版应坚持以下边界：

> **桌面应用 + Markdown 只读阅读 + 左侧 AI 对话 + 自定义兼容接口 + 清晰可控的上下文 + 本地记录 + 低干扰的狐狸助手。**

产品价值来自顺畅的阅读与提问体验；Fox 的大尾巴与竖耳朵，则将这种体验转化为可识别、可感知的品牌特色。
